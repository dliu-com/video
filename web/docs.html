How it works

video.dliu.com hosts videos that anyone can watch and that other dliu.com sites can embed. There are no servers: files sit in S3, CloudFront delivers them, and one small Lambda function runs only when the owner signs in or changes a video.

Running costs

Everything is billed per use. With nobody watching, the only charge is storing the videos in S3.

Security

Anyone can watch; only the owner, signed in with Microsoft, can upload, edit or delete.

How this site is tested

Every 15 minutes, status.dliu.com visits this site like an ordinary visitor who isn't signed in. It opens the public pages, makes sure the locked doors are still locked, and asks the site to check its video list and sign-in settings. It never signs in and never changes anything.

What is checked

  • Pages The home page and these docs open. If down, visitors get an error page instead of the site.
  • Video list and storage The public list of videos can be read. If down, the home page is empty and videos don't open.
  • Player and embeds The watch page, the embed player that other sites such as the blog use, and the player program open. If down, videos don't play here or in the blog.
  • Microsoft sign-in The sign-in button goes to Microsoft and the site can read its sign-in settings. If down, the owner can't sign in; watching still works.
  • Owner tools lock Uploads, edits and deletes on the website refuse anyone who isn't signed in. If it ever lets a guest in, it is reported as down.
  • Tools API lock The API for tools and AI agents refuses requests without a Microsoft token. If it ever lets a guest in, it is reported as down.
Technical details: guest checks

Every check uses GET or HEAD only; sends no cookies, no Authorization header and no query string; does not follow redirects; uses the user agent dliu-status-bot/1.0 (+https://status.dliu.com/docs); and times out after 10 s. Match content types by prefix.

Technical details: the /health self-check

GET https://video.dliu.com/health (HEAD also works). No sign-in: CloudFront forwards no cookies, Authorization header or query string, and the Lambda reads no request data. Cached at CloudFront for 60 s. Each check has 4 s; over 1 s is warn (common for the first request after the Lambda has been idle). It answers application/health+json: 200 for pass or warn, 503 for fail; output is only slow, timeout or read failed.

What isn't tested

  • Signing in at Microsoft and getting a session
  • Uploading, replacing, editing and deleting videos and posters
  • Converting uploads into streaming versions
  • Using the tools API with a real Microsoft token
  • Playing a particular video, because which videos exist changes
